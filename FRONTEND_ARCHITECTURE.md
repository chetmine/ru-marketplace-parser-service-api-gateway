# Руководство по архитектуре Frontend приложения

Добро пожаловать в проект! Этот документ предназначен для Junior Frontend-разработчика и описывает архитектуру клиентской части приложения, а также правила взаимодействия с сервером. Пожалуйста, внимательно изучи этот гайд, он поможет тебе быстрее влиться в работу.

## 1. Основной стек технологий

- **Фреймворк/Библиотека:** React
- **Язык:** JavaScript (ES6+)
- **Управление состоянием:** Встроенные возможности React (например, `useState`, `useReducer`, Context API). Сторонние стейт-менеджеры (Redux, MobX и т.д.) не используются для упрощения поддержки и снижения порога входа.

---

## 2. Архитектура приложения (MVC в контексте React)

Мы придерживаемся логического разделения на слои по паттерну **MVC (Model-View-Controller)**, чтобы отделить бизнес-логику от отображения и сетевых запросов. В контексте нашего React-приложения это выглядит следующим образом:

### Model (Модель)
Модель отвечает за данные приложения и бизнес-правила. В нашем случае к слою Модели относятся:
- Сервисы для работы с API и WebSocket.
- Управление клиентским хранилищем (например, хранение токенов).
- Подготовка, трансформация и валидация данных, полученных от сервера, перед передачей их в контроллеры.

### View (Представление)
Слой отображения отвечает исключительно за рендеринг пользовательского интерфейса (UI):
- Это "глупые" (dumb/presentational) React-компоненты: кнопки, формы, таблицы, карточки.
- Они ничего не знают о том, откуда берутся данные и как они сохраняются на сервер.
- View получает данные только через `props` и сообщает о действиях пользователя через функции-коллбэки.

### Controller (Контроллер)
Контроллер выступает связующим звеном между Представлением (View) и Моделью (Model).
- **Смарт-компоненты и Хуки:** В React роль контроллеров играют контейнерные компоненты или кастомные хуки. Они обращаются к Модели за данными, сохраняют их в локальном стейте React и спускают вниз во View.
- **REST Controller на стороне клиента:** На бэкенде логика разбита по доменам (например, `AuthController`, `SubscriptionController`). На фронтенде должна быть аналогичная структура: отдельные логические модули-контроллеры, которые инкапсулируют эндпоинты сервера и предоставляют удобные методы для работы с определенной сущностью (например, контроллер авторизации, контроллер подписок).

## 3. Взаимодействие с сервером

Серверная часть проекта предоставляет два канала связи с клиентом: **REST API** (основной канал) и **WebSocket** (для данных в реальном времени).

### 3.1 REST API
Используется для классических разовых запросов: получения данных по запросу, отправки форм, создания записей и авторизации.
- **Схема работы:** Клиент отправляет HTTP-запрос к нужному серверному REST Controller'у, сервер обрабатывает его и возвращает ответ в формате JSON.
- **Архитектура запросов:** Все запросы должны быть сгруппированы в отдельные сервисы-контроллеры на стороне клиента. Нельзя вызывать `fetch` напрямую из компонента View. Компонент-контроллер вызывает метод из сервиса API, обрабатывает ответ (или ошибку) и обновляет стейт.

### 3.2 WebSocket (WS)
Используется для двунаправленного постоянного соединения между клиентом и сервером.
- **Схема работы:** После успешной авторизации фронтенд устанавливает WebSocket соединение с сервером.
- **Роль WS:** Сервер асинхронно пушит (отправляет) события клиенту (например, уведомления, изменение статусов подписок и т.д.). Фронтенд слушает эти события и реактивно обновляет нужные части UI.
- **Обработка разрывов:** Обязательно должна быть реализована логика обработки отключения и автоматического переподключения к WebSocket-серверу (reconnection logic) на случай проблем с сетью.

## 4. Авторизация и безопасность (JWT: Access + Refresh)

В проекте реализована система авторизации на основе **JWT (JSON Web Token)** с использованием пары токенов: **Access Token** и **Refresh Token**.

### Access Token
- **Назначение:** Токен доступа. Именно его фронтенд использует для подтверждения личности пользователя при каждом запросе к защищенным эндпоинтам REST API и при подключении к WebSocket.
- **Передача:** Токен должен прикрепляться к HTTP-запросам (обычно через заголовок `Authorization: Bearer <токен>`).
- **Срок жизни:** Короткий (в целях безопасности).

### Refresh Token
- **Назначение:** Токен обновления. Используется **только** для запроса у сервера новой пары токенов (нового Access и нового Refresh), когда текущий Access Token истек.
- **Срок жизни:** Длинный. Его нужно хранить в безопасном месте на клиенте и защищать от перехвата.

### Жизненный цикл авторизации (Флоу)
1. **Логин:** Пользователь вводит учетные данные. Клиентский контроллер авторизации отправляет их на сервер (на бэкендовый `AuthController`).
2. **Получение токенов:** При успехе сервер возвращает пару Access и Refresh токенов. Фронтенд сохраняет их.
3. **Авторизованные запросы:** Ко всем последующим запросам фронтенд прозрачно для компонентов добавляет Access Token.
4. **Протухание Access Token'а:** Рано или поздно токен истекает. При попытке сделать с ним запрос, сервер вернет ошибку (статус `401 Unauthorized`).
5. **Процесс обновления (Refresh):**
   - Фронтенд перехватывает ошибку `401`.
   - Приостанавливает упавший запрос.
   - Берет сохраненный Refresh Token и отправляет специальный фоновый запрос на сервер для обновления сессии.
   - Сервер возвращает новые Access и Refresh токены.
   - Фронтенд сохраняет новые токены и автоматически повторяет первоначальный запрос с новым Access Token'ом.
6. **Выход (Logout):** Если Refresh Token тоже оказался недействительным или истек (или сервер вернул ошибку при попытке обновления), процесс обновления прерывается. Фронтенд очищает локальные данные о пользователе и токенах, после чего перенаправляет пользователя на страницу входа.

## 5. Общие рекомендации по написанию кода

1. **Разделение ответственности:** Держи логику работы с сетью отдельно от UI-компонентов.
2. **Глобальные состояния через Context:** Поскольку мы не используем Redux, общие данные приложения (например, данные профиля текущего пользователя, токены, объект WebSocket соединения) рекомендуется хранить и распространять с помощью встроенного React Context API.
3. **Единая точка входа для API:** Для удобной работы с JWT и обработки обновления токенов рекомендуется настроить единый сервис сетевых запросов (например, с использованием паттерна Interceptor/Перехватчик), который будет централизованно подставлять Access Token и автоматически обрабатывать логику Refresh-токена.
4. **Проектируй от данных к UI:** Сначала продумай, какие данные нужны (Model), как они будут запрашиваться и обновляться (Controller), и только потом рисуй интерфейс (View).

Желаем успешной работы и написания чистого, структурированного кода! Если возникнут сомнения — обращайся к этому документу как к базовому ориентиру.
