# Описание архитектуры бэкенд-приложения (Parser)

Добро пожаловать в проект! Этот документ предоставляет высокоуровневое описание архитектуры серверной части (бэкенда) нашего приложения. Он предназначен для понимания общих принципов работы системы, используемых технологий и взаимодействия ключевых компонентов.

## 1. Технологический стек

Серверная часть приложения построена на базе современных, надежных и масштабируемых технологий:

*   **Язык программирования:** Java 21 (современная версия, обеспечивающая высокую производительность и безопасность).
*   **Фреймворк:** Spring Boot (отраслевой стандарт для создания микросервисов и корпоративных приложений на Java).
*   **Основная база данных:** PostgreSQL (мощная и надежная реляционная система управления базами данных для постоянного хранения информации).
*   **Кэширование и быстрое хранилище:** Redis (используется для хранения временных данных, управления сессиями и кэширования для ускорения работы приложения).
*   **Брокер сообщений:** RabbitMQ (обеспечивает асинхронную обработку задач и надежную связь между различными частями системы).
*   **Безопасность:** Spring Security с использованием JWT (JSON Web Tokens) для безопасной аутентификации и авторизации пользователей (Access и Refresh токены).
*   **Взаимодействие с клиентом:** REST API (основной канал связи) и WebSockets (для передачи данных в реальном времени).

## 2. Общая архитектура системы

Приложение спроектировано с учетом принципов модульности и разделения ответственности (Separation of Concerns). Основные компоненты системы и их роли:

### 2.1. API Gateway и маршрутизация (REST & WebSockets)

Приложение выступает в роли единой точки входа для клиентских запросов.
*   **REST API:** Обрабатывает классические запросы (например, авторизация, получение данных профиля, отправка форм). Все запросы проходят через слои безопасности и маршрутизируются к соответствующим контроллерам.
*   **WebSockets:** Обеспечивает постоянное двунаправленное соединение с клиентом для мгновенной передачи событий (например, уведомления об изменениях статусов).

### 2.2. Слоистая архитектура приложения

Кодовая база структурирована по слоям, каждый из которых выполняет свою специфическую функцию:

*   **Слой контроллеров (Controllers):** Принимает входящие HTTP-запросы от клиентов, проверяет входные данные и передает их на обработку в слой бизнес-логики.
*   **Слой сервисов (Services):** Содержит ядро бизнес-логики приложения. Здесь реализуются правила работы с данными, вычисления и координация процессов. Этот слой не зависит от того, как данные были получены (через REST, WebSocket или RabbitMQ).
*   **Слой доступа к данным (Repositories):** Отвечает за взаимодействие с базой данных PostgreSQL. Использует Spring Data JPA для удобного и безопасного выполнения запросов к БД.
*   **Слой данных (Entities & DTOs):**
    *   **Entities:** Объекты, напрямую отображаемые на таблицы в базе данных PostgreSQL.
    *   **DTOs (Data Transfer Objects):** Объекты, используемые для передачи данных между клиентом и сервером. Позволяют скрыть внутреннюю структуру БД и передавать только необходимую информацию.
*   **Инфраструктурный слой (Infrastructure/Config):** Содержит настройки подключения к внешним сервисам (БД, Redis, RabbitMQ, почтовые сервисы) и конфигурацию самого приложения (например, настройки безопасности, документации API).

### 2.3. Асинхронная обработка и интеграции

Для повышения производительности и отказоустойчивости система использует асинхронные механизмы:

*   **RabbitMQ:** Используется для фоновой обработки задач, которые не требуют мгновенного ответа пользователю (например, отправка email-уведомлений, сложная обработка данных). Это позволяет API оставаться быстрым и отзывчивым.
*   **Фоновые задачи (Scheduled Tasks):** В системе предусмотрены регулярные автоматические процессы, например, очистка устаревших данных (cleanup pending users).
*   **Почтовый сервис:** Интеграция со сторонними SMTP-серверами (например, Gmail) для отправки транзакционных писем.

## 3. Масштабируемость и развертывание

*   Приложение контейнеризовано с использованием Docker (описано в `Dockerfile` и `docker-compose.yml`), что обеспечивает независимость от среды выполнения и простоту развертывания на любых серверах.
*   Архитектура без сохранения состояния (stateless) в слое API (состояние сессий управляется через JWT и Redis) позволяет легко масштабировать приложение горизонтально, добавляя новые экземпляры серверов при возрастании нагрузки.

## Заключение

Архитектура бэкенд-приложения построена на проверенных корпоративных стандартах (Java, Spring Boot, PostgreSQL) с добавлением современных инструментов для асинхронности (RabbitMQ) и скорости (Redis). Это обеспечивает надежную, безопасную и масштабируемую основу для дальнейшего развития продукта.
